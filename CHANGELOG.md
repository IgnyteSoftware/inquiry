# Changelog

All notable changes to Inquiry are documented in this file.
The format is based on [Keep a Changelog](https://keepachangelog.com/en/2.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- `INQ117` is a new build warning for a non-nullable column that sets `UseDatabaseDefault = true` with no `DefaultExpression` on an entity that generates DDL. Generated inserts omit the column and the generated table has no default for it, so those inserts always failed with a `NOT NULL` error at run time. Add a `DefaultExpression`, or set `GenerateDdl = false` when the deployed table has its own default. Projects that treat warnings as errors must fix or suppress it.
- The migrations recipe now has a runnable DbUp sample for SQL Server, `samples/Inquiry.SchemaEvolution`. It deploys a new database, baselines an existing one without rerunning its first script, widens a column, runs the old and new application versions side by side while both table types exist, and then retires the old type in a later release. The guide adds the deployment order, separate deployment and application permissions, failure recovery and the limits of each provider. The application principal needs `EXECUTE` and `REFERENCES` on each generated table type. The guide used to name only `REFERENCES`, which SQL Server rejects with error 229.
- An entity mapping guide explains inferred table and column names, explicit column opt-in, nullability, typed foreign keys, and who owns the schema. Its table shows which columns each mapping inserts, updates, omits and reads back, covering `DefaultExpression`, `UseDatabaseDefault`, generated keys, computed columns, CLR initializers and `GenerateDdl = false`. Its example program runs against SQLite in the package checks and prints the SQL of each statement, so the page shows that an assigned value does not override a `UseDatabaseDefault` column on insert.
- A row locking guide lists the lock clause each provider generates for every `InquiryLockMode`, what each mode does while another transaction holds the row, and the exception `UpdateNoWait` raises on each provider. It shows a read-change-write example and a work-queue claim example that the integration tests run on PostgreSQL, MySQL, MariaDB, SQL Server and Oracle, and lists lock combinations that compile but do not lock as written.
- The interceptors guide shows how to turn on N+1 detection: register it with `AddInquiryNPlusOneDetection`, then wrap each request or job in `InquiryNPlusOneScope.BeginScope()`. It covers the threshold, nested scopes, disposal and the logging requirement.
- `INQ111` is a new build error for an Inquiry store method that is static or generic, has a `ref`, `in`, `out`, `ref readonly` or `scoped` parameter, or returns by reference. The generator cannot repeat those signatures in the generated implementation. Before, such a method failed with compiler errors about the generated code instead. The message names the method and each unsupported part. Declare a non-generic instance method with by-value parameters, or remove the Inquiry attribute and implement the method yourself.
- `INQ113` is a new build error for a store whose concurrency-token shape is not supported: an upsert on an entity with `[InquiryConcurrencyToken]`, reported at each upsert method, or a database-generated token on a dialect other than SQL Server, reported at the store. It replaces the `INQ006` that token upserts reported at the store, which named the store as if it were a method.

### Changed

- **Breaking:** `InquiryForeignKeyAttribute.ReferencedTable` and `ReferencedColumn` are now declared `string?`. They were declared non-null but returned `null` when a type-safe constructor was used: both for `[InquiryForeignKey(typeof(T))]`, and `ReferencedTable` for `[InquiryForeignKey(typeof(T), "Name")]`. Code that reads these properties through reflection now gets a nullable warning where the value can be absent. Generated code is unchanged.
- **Breaking:** `INQ116` is a new build error for `[InquiryForeignKey(typeof(T), "Name")]` when `T` has no property called `Name`. Before, the generator used the string as a raw column name and reported nothing, so a typo such as `"CategoryId"` for `CategoryID` produced a foreign key to a column that might not exist. A name that equals a column name but no property name also fails. To upgrade, pass the property with `nameof`, or use the string form `[InquiryForeignKey("Table", "Column")]` for physical names.
- **Breaking:** Every package now targets `net10.0` and `net11.0`. The `net8.0` and `net9.0` targets are removed, because Microsoft ended support for .NET 8 and .NET 9 on 2026-11-10. To upgrade, move the consuming project to .NET 10 or later. Projects that stay on .NET 8 or .NET 9 can keep using `1.0.0-preview.13`, which receives no further fixes.
- **Breaking:** Every `Ignyte.Inquiry*` package now depends on `Ignyte.Inquiry`, and on any other Inquiry package it uses, at exactly its own version, such as `[1.0.0]`. Before, the dependency was a minimum, so a provider could restore with a different `Ignyte.Inquiry`. The provider's generator then read attributes from another release and reported unhelpful mapping errors. Now NuGet rejects the mix at restore. Two Inquiry packages at different versions fail with `NU1107`. A direct `Ignyte.Inquiry` reference older than the provider fails with `NU1605`. A direct reference newer than the provider warns `NU1608`, which fails restore only under `TreatWarningsAsErrors`. To upgrade, set every `Ignyte.Inquiry*` reference to the same version, and update them together. Packages that were published before this change keep their minimum ranges.
- The auditing guide and the `InquiryCreatedAtAttribute` documentation no longer say that `DefaultExpression` alone gives database-clock stamping. Generated inserts still send the property value; database stamping also needs `UseDatabaseDefault = true`. The schema DDL guide no longer says that a nullable column with a default can never be `NULL` (`INQ066`), and its computed-column example now includes the PostgreSQL expression that mixed-case column names need.
- The aggregates guide uses the correct `InquiryAggregateFunction` enum and no longer says that aggregates ignore `[InquiryWhere]`. It explains predicate parameters, nullable results and the count shapes, and its example program runs against SQLite in the package checks. The `InquiryLockMode` documentation no longer says that a lock outside a transaction is an error: the query runs, and the lock ends with the statement.
- **Breaking:** Suppressing or lowering an Inquiry error no longer produces a store that builds and throws `NotSupportedException` when it runs. Two configurations that built before now fail with CS8795 at each rejected method:
  - A store whose methods were all rejected, or whose entity is invalid (`INQ008`), while the rejecting error is suppressed or lowered, for example with `<NoWarn>`.
  - A suppressed provider facet error, such as SQL Server's `INQ076`, while `INQ039` is lowered.
  To upgrade, fix the declaration the suppressed error reports. Only `INQ039` still opts a method into a `NotSupportedException` stub when it is lowered project-wide, and only for the methods that report `INQ039`.
- A store whose methods are all rejected, including a store with a rejected concurrency-token shape, now keeps its generated constructor. The build reports the Inquiry error and CS8795 at each rejected method, without the extra CS7036 for a missing constructor. A generated `[InquiryGenerateInterface]` interface lists only the methods the generator implemented.
- **Breaking:** `INQ114` is a new build error for `[InquiryStoredProcedure]` methods that Inquiry cannot run on the target database. Procedures are supported on SQL Server and Oracle only. Before, a procedure method on SQLite, PostgreSQL, MySQL or MariaDB compiled and failed when called. On Oracle, `ReturnsValue = true`, a string or `byte[]` `OutputParameter`, a string or `byte[]` INOUT parameter without a `Length`, and OUTPUT or INOUT values of other non-numeric types also compiled and then failed in ODP.NET. To upgrade, remove procedure methods from stores on the four other providers, or call the SQL through `IInquiry`. On Oracle, return a status through an `OUT NUMBER` parameter with `OutputParameter`, and set `[InquiryParameter(IsInputOutput = true, Length = n)]` on string and `byte[]` INOUT parameters. The procedure guide now has a provider capability table, and each supported feature has live tests.
- **Breaking:** `INQ039` now reports locking selects that the database rejects every time they run. On PostgreSQL, `Distinct = true` with any `LockMode` fails with SQLSTATE `0A000`. On Oracle, `Distinct = true` fails with ORA-01786, and offset paging (`Paged = true`, or an `InquiryPagedResult<T>` return) fails with ORA-02014. These methods compiled before and threw on every call. Remove `Distinct` or the paging, or remove the lock. MySQL, MariaDB and SQL Server still accept both combinations.
- **Breaking:** Generated methods that return `InquiryPagedResult<T>` now send the page `SELECT` and the `COUNT` as one command with two result sets, on all six providers. Before, they ran two commands, each with its own connection from the pool. Now a call makes one round trip and uses one connection. Interceptors see one command, whose text holds both statements, and telemetry records one `QUERY_MULTIPLE` operation instead of two. The page and the total are still two statements, so they agree only inside a snapshot or serializable transaction; the `InquiryPagedResult` documentation said before that they shared a connection, which was not true. A custom `IInquiry` implementation must now implement `QueryMultipleAsync` to run these methods, or forward it to the built-in implementation. The default throws `NotSupportedException`.
- **Breaking:** When a grid read fails and disposing the grid then also fails, `DisposeAsync` now throws `AggregateException` with the read failure first, followed by the cleanup failures. Before, the cleanup failure replaced the read failure. This applies to `QueryMultipleAsync` and to generated eager-load and `InquiryPagedResult<T>` methods. A cancelled read in that case surfaces as an `AggregateException` whose first inner exception is the `OperationCanceledException`. Code that catches `OperationCanceledException` around these calls should also inspect `AggregateException.InnerExceptions` if cleanup can fail.
- Large buffered list reads allocate less. When a result passes 16 rows and no capacity hint covers it, the rows collect in arrays rented from `ArrayPool<T>.Shared` and are copied once into a list of the exact size, instead of growing the list by doubling. A 100,000-row `SelectAll` of the sample `Product` entity allocates about 1.3 MB less, and a 1,000-row one about 8 KB less. The result is still a `List<T>`, and its `Capacity` now equals its `Count`. This applies to unpaged generated list methods, stored-procedure lists, `IInquiry.QueryListAsync` and `IInquiryTransaction.QueryListAsync`, and `InquiryGridReader.ReadListAsync`. Lists that eager-loading methods build for their parent rows are not changed.
  - Results of 16 rows or fewer, and lists whose capacity hint covers the result, such as paged reads, allocate exactly as before.
  - Results of 28 to 32 rows without a hint allocate up to 40 bytes more. A hint smaller than the result can cost the same 40 bytes near other sizes.
  - The first large read of an entity type on a thread, and the first one after the pool releases idle arrays, allocates the rented arrays as well.
- Non-query, scalar and bulk-insert calls that receive a cancelable token, such as an ASP.NET Core request token, no longer allocate anything beyond the token registration in the steady state. Before, each call allocated a race object, a boxed registration and up to three async state machines, even when the driver had already finished. Inquiry reuses the object that tracks a running call, so a call that starts while many others are in flight can still allocate one. The cancellation behaviour is unchanged: cancellation that beats the driver still throws `OperationCanceledException` with the caller's token, and a result that beat the cancellation is still returned.
- A short `Compare.In` list of integers now binds as scalar parameters, `col IN (@ids_in0, @ids_in1, …)`, instead of one JSON array, table-valued or array parameter, which costs more for a few values. The list pads to the next power of two by repeating its last value, so each `IN` criterion has a small fixed set of statement texts. The longest list bound this way is 4 values on SQLite, 16 on SQL Server and MySQL, 8 on MariaDB and 32 on Oracle; PostgreSQL keeps its array for every length. Only integers bind this way, including numeric enums and converters to an integer, and on SQL Server not a column with an explicit `SqlType`; strings, `char`, decimals, temporal values and other types keep the collection parameter, because each provider converts them to its own SQL type, width and collation. Longer, empty and `null` lists, lists whose count is not known without enumerating them, and methods that also have a `NOT IN` criterion bind as before. Interceptors, logs and the SQL Server plan cache see the scalar text for short lists. On SQL Server, a short integer list no longer uses the generated table type, so a missing `Inquiry_Tvp_*` type or a missing `EXECUTE` permission on it now fails only a call with more than 16 values; run `ProviderArtifactsValidationSql` during deployment. No code change is needed.
- Editing one entity, view, projection or `[InquiryAdHoc]` DTO now regenerates only that type's materializer, not every materializer in the project. Editing a store, or a model that a store reads, now regenerates only the stores that read it. A store reads its own entity, that entity's relation children and junctions, the projections its methods return, and its stored-procedure result types. This reduces generator work after an edit in the IDE, which keeps the generator state between edits. Command-line builds run the generator from scratch and are unaffected. Generated code is unchanged. The schema still regenerates after any entity edit.

### Fixed

- A scalar or aggregate method that returns `decimal`, and whose provider returns a floating-point value, now gives the same result on .NET 10 and .NET 11. SQLite returns `SUM` and `AVG` over a `REAL` column as a `double`, and .NET 11 converts `double` to `decimal` exactly, so a sum of 21.99 came back as 21.98999999999999843... on .NET 11. The conversion now follows the .NET 10 algorithm on both runtimes, which rounds a `double` to 15 significant digits and a `float` to 7.
- On Oracle, a stored-procedure method with a `Guid` or `DateTime` input now runs. Procedure parameters took their `DbType` from a mapping that ignores the provider, and ODP.NET rejects `DbType.Guid` and `DbType.DateTime2`. They now use the same choices as entity columns: `Guid` binds as `RAW(16)`, `DateTime` as `TIMESTAMP`, `bool` as `NUMBER(1)`, `DateOnly` as `DATE` and `TimeOnly` as `INTERVAL DAY TO SECOND`, for nullable parameters too. SQL Server procedure binding is unchanged.
- Every `InquiryGridReader` read now reports cancellation with the caller's token. `ReadSingleOrDefaultAsync`, `ReadGeneratedSingleOrDefaultAsync`, `ReadForEachAsync`, `ReadRowsAsync` and `ReadStreamAsync` rethrew what the driver raised: an `OperationCanceledException` with the provider's own token, or a native driver error. They now throw an `OperationCanceledException` that carries the caller's token, with a native error as its inner exception, as `ReadListAsync`, `ReadScalarAsync` and the single-command paths do. Generated eager loads read their child result sets through these methods. A driver error with no cancellation requested is unchanged. Only driver calls are treated this way: a failure from a materializer or a row callback surfaces as it was thrown, on every grid read, even when the token is already cancelled.
- **Breaking:** Disposing an `InquiryNPlusOneScope` while a nested scope is still active now throws `InvalidOperationException` and leaves both scopes as they were, the same rule as filter and audit scopes. Before, it turned detection off, and disposing the nested scope afterwards made the disposed outer scope count and warn again. Nested `using` blocks dispose in order and are not affected. Repeated disposal still does nothing.
- The optional lint `INQ066` no longer says that new rows of a nullable column with a `DefaultExpression` can never be `NULL`. Generated inserts send the property value, so a `null` property stores `NULL`, and the default applies only when an insert omits the column. The message now says so. When the lint fires is unchanged.
- Table names, column names and other attribute strings that contain a line break, tab, NUL or another control character now produce generated code that compiles. Before, a line break produced a compile error in the generated file, and a NUL stopped the generator with warning `CS8785`, so the store had no generated code. The generated string constants keep the exact value you wrote. In the generated documentation, the characters that would break it show as C# escapes, such as `\0`.
- A SQL Server stored procedure with a `byte[]` `OutputParameter` now runs. Before, SqlClient rejected the call with "the Size property has an invalid size of 0".
- `[InquiryCount]` applies its `[InquiryWhere]` criteria, including criteria from a specification attribute. Before, a criterion that takes no value, such as `Compare.IsNull`, compiled and the method counted every row. A criterion that takes a value, such as `[InquiryWhere("CategoryID")]` on `CountInCategoryAsync(int? categoryID, ...)`, now binds to the method parameter like a predicate select. Before, it reported `INQ006`. Counts without criteria are unchanged.
- **Breaking:** `INQ115` is a new build error for `[InquiryWhere]` criteria, direct or from a specification attribute, on an operation that does not apply them. Before, these declarations compiled and the criteria were ignored, so the method returned unfiltered results. The affected operations are `[InquirySelectAll]`, `[InquirySelectAllByField]`, `[InquirySelectOneByKey]`, `[InquirySelectTopByOrder]`, `[InquiryGroupCount]`, `[InquiryKeysetPage]`, `[InquiryFullTextSearch]`, the eager selects, `[InquiryRestoreOneByKey]`, `[InquiryInsert]`, `[InquiryUpsert]`, `[InquiryBulkInsert]` and `[InquiryStoredProcedure]`. To upgrade, use `[InquirySelectAllByPredicate]` to filter rows or `[InquiryCount]` to count them, or remove the criteria if the method should read every row. Some declarations that already failed now report `INQ115` in place of `INQ006` or `INQ020`.
- A `[InquirySelectAll]` or `[InquirySelectAllByField]` method with a `LockMode` that returns an `[InquiryProjection]` type now locks the rows it reads. Before, the projection query had no lock clause or table hint, so another transaction could change the rows. Ordered and paged projections were already locked.
- On SQL Server, a locking select on a table that has a column with the same name as the table now runs. The table hint used to follow the first occurrence of the name, which was the column, and SQL Server rejected the query with "Incorrect syntax near the keyword 'with'". The hint now always follows the table after `FROM`.
- A runtime-parameterized global filter (`ContextKey`) no longer shares its parameter name with another value in the same command. Before, an entity property named `__gf_TenantId` beside a `TenantId` filter produced two `@__gf_TenantId` parameters. PostgreSQL then compared the tenant column to the wrong value and returned another tenant's rows. SQLite, SQL Server, MySQL, MariaDB and Oracle failed the command. The filter parameter now moves to a free name, such as `@___gf_TenantId`, when a mapped property uses its name. A criterion, JSON-path value or `[InquirySet]` parameter with a filter parameter's name binds under a numbered name, such as `@__gf_TenantId2`. Generated SQL is unchanged for every other declaration.
- Offset-paged methods no longer share a parameter name between the page bounds and a filter value. Before, a field read or criterion on a property named `__offset` or `__limit`, in any case, or a JSON-path criterion such as `$.__limit`, bound a second `@__offset` or `@__limit` parameter. PostgreSQL then used the filter value as the page offset or limit and returned the wrong page. SQLite, SQL Server, MySQL, MariaDB and Oracle failed the command. On an entity that maps a property with a paging name, ignoring case, that paging parameter now gains leading underscores, such as `@___offset`, in every offset-paged method on the entity. A criterion or JSON-path value with a paging name binds under a numbered name, such as `@__limit2`. Keyset paging names cannot collide and do not change. Generated SQL is unchanged for every other declaration.
- An interpolated SQL string that has no values now sends its literal braces correctly. `InquirySql.Sql` and the interpolated `IInquiry` and `IInquiryTransaction` methods passed the doubled braces through, so `$"UPDATE t SET prefs = '{{}}'"` reached the database as `'{{}}'`. A string with at least one value was already correct.
- A second `AddInquiryTelemetry` call now applies its options. Before, only the first call counted, and the Aspire methods such as `AddInquiryPostgreSql("name")` make that first call themselves. `AddInquiryTelemetry(o => o.RecordCommandText = false)` after one of them did nothing, so spans and logs still carried the SQL text. A repeat call now configures the options of the first registration.
- `ExecuteScalarAsync` reports a result that cannot be converted to the requested type as a failure only. Before, interceptors received `CommandExecutedAsync` and then `CommandFailedAsync` for the same command, and telemetry recorded a successful command. This applies to the interpolated and generated scalar paths, inside and outside a transaction.
- **Breaking:** A transaction no longer hides the database error behind its own cleanup. Inquiry rolls back as cleanup when a transaction is disposed without a commit, and after `CommitAsync` or `RollbackAsync` fails. Drivers reject that rollback when the transaction has already ended or the connection is lost, and Inquiry reported the rejection. A command that failed on a lost connection then surfaced as `InvalidOperationException` on SQL Server, or `ObjectDisposedException` on PostgreSQL, when the `await using` block or `ExecuteInTransactionAsync` unwound. A commit that PostgreSQL rejected, such as a serialization failure or a deferred constraint, surfaced as `AggregateException`, so a `catch` on the provider exception did not match. The cleanup rollback is now best effort and its failure is not reported, so the caller gets the provider exception itself. Generated batch methods that own their transaction follow the same rule. Failures to dispose the transaction or the connection are still reported, and a cleanup rollback that does not finish in five seconds still reports `TimeoutException`. Code that read the provider error from an `AggregateException` around `CommitAsync` or `RollbackAsync` must also catch the provider exception.
- On PostgreSQL, a `Compare.In` list over a `byte` column, a byte-backed enum column or a `char` column now runs. The list was bound as `byte[]` or `char[]`, which Npgsql sends as `bytea` and `text`, so PostgreSQL rejected `= ANY(...)` with SQLSTATE `42809`. The list now binds as `smallint[]` or `text[]`. Scalar predicates on these columns already worked.
- On SQL Server, a bulk insert no longer corrupts a large `VARBINARY(MAX)` value that comes from a value converter. The provider turned on `SqlBulkCopy.EnableStreaming`, which reads such a value 4 KB at a time, and Inquiry ran the converter again for each read. A converter that returns different bytes on each call, such as the AES-GCM encryption in the column encryption guide, then stored a value spliced from several encryptions. Every value over 4,096 bytes was written without an error and could not be decrypted. A converter that always returns the same bytes was correct but ran once for every 4 KB. Streaming is now off, so each value is converted once. Rows that an earlier bulk insert corrupted cannot be recovered and must be written again.
- **Breaking:** On SQL Server, a bulk insert now follows the rules of an ordinary `INSERT`. The provider ran `SqlBulkCopy` with its default options, so the server skipped `FOREIGN KEY` and `CHECK` constraints and marked them as not trusted, stored the column default in place of a `null` property, and did not fire insert triggers. A row with a dangling foreign key or a failed check was accepted without an error, while `[InquiryInsert]`, PostgreSQL `COPY` and `MySqlBulkCopy` reject it. The provider now sets `CheckConstraints`, `KeepNulls` and `FireTriggers`. A bulk insert that wrote rows that break a constraint now fails with error 547, a `null` on a column with a default stores `NULL`, and insert triggers fire once for each batch. To upgrade, fix the rows that break a constraint. Constraints that an earlier bulk insert left untrusted stay untrusted until you run `ALTER TABLE ... WITH CHECK CHECK CONSTRAINT ...`, which fails while such rows exist.
- On SQLite, a `Compare.In` list over a `Guid`, `DateTime`, `DateTimeOffset`, `TimeOnly`, `byte[]` or `float` column now matches rows. The list was sent as JSON text in a different form from the one Microsoft.Data.Sqlite stores: lower-case GUIDs against upper-case, `2026-07-10T12:34:56.1230000` against `2026-07-10 12:34:56.123`, base64 text against a BLOB, and `1.1` against a `float` widened to a double. SQLite compares the two as written, so a select returned no rows and a batch delete by keys deleted nothing, with no error. This also applied to a converter whose provider type is one of these. Each element is now sent in the stored form, and a `byte[]` list is sent as hex and compared through `unhex`, which needs SQLite 3.41 or later. Lists of integers, strings, `bool`, `double`, `decimal` and `DateOnly`, and `NOT IN` lists, were already correct.
- On SQL Server, a method that returns the written entity now returns a column with an explicit `SqlType` unchanged. Returning inserts, updates, upserts and soft deletes pass the row through a table variable, which was declared with the type Inquiry infers from the property and not with the `SqlType`. A `decimal` column declared `SqlType = "decimal(19,4)"` went through `DECIMAL(18,2)`, so the table stored `12.3456` and the method returned `12.35`. A value outside the inferred type failed the statement. The table variable now takes the declared `SqlType`. A `rowversion` or `timestamp` column is still read as `BINARY(8)`.
- On SQL Server, `ProviderArtifactsValidationSql` no longer reports a correct table type as mismatched when its column is declared `SqlType = "datetime"`. The check expected scale 0, and SQL Server reports scale 3 for `datetime`, so a deployment that runs the validation failed on every such `Compare.In` column. The generated table type and the queries that use it were already correct.
- A store whose partial declarations each repeat `: InquiryStore<T>` now builds. Both declarations produced the same generated file, which stopped the generator with warning `CS8785`, so the project lost every generated store, materializer and registration and reported `CS8795` on each store method. The store is now generated once, with the methods of all its declarations.
- A `[InquirySelectAllByField]` method with `OrderBy` that returns `IAsyncEnumerable<T>` now builds. The generated body returned the buffered list call, so the build failed with `CS0029` in the generated file. The select declarations guide lists this shape as supported. The buffered form and offset paging are unchanged.
- `[InquirySelectOneByKeyEager(IncludeDeleted = true)]` now loads the to-one relations of a soft-deleted parent. The method returned the parent, but each reference such as `Order.Customer` came back `null`, because its query looked the parent up again with the soft-delete filter. Collections and many-to-many relations already loaded. Methods without `IncludeDeleted` are unchanged.
- `Converter = typeof(X)` on `[InquiryForeignKey]` is now applied. A property mapped by `[InquiryForeignKey]` alone ignored the converter, with no error: the column took the type of the model, and reads and writes passed the model value to the driver and failed at run time. A strongly typed foreign key needed a second `[InquiryColumn(Converter = ...)]` on the same property. `Length`, `SqlType` and the other named values were already read from the foreign-key attribute.

## [1.0.0-preview.13] - 2026-11-02

### Added

- `[InquiryInclude(nameof(...))]` limits an `[InquirySelectAllEager]` or `[InquirySelectOneByKeyEager]` method to the relations it names. Apply it once per relation. The method's command then carries only the parent `SELECT` and the named relations' `SELECT`s, and adding another relation to the entity does not change it. Methods without the attribute still load every relation. A name that is not a relation on the entity, a relation whose type is not an `[InquiryTable]` entity, a name given twice, or the attribute on a method that is not an eager method reports the new build error `INQ107`, which names the property.
- `[InquirySelectAllEager]` methods can return `Task<IReadOnlyList<TEntity>>`. The list form sends the same single command as the `IAsyncEnumerable<TEntity>` form, with the same filters and the same graph, and closes the reader before the task completes. The streaming form is unchanged. The sample `CatalogService` now uses the list form.
- `[InquiryJson]` properties can serialize through a source-generated `System.Text.Json` `JsonSerializerContext`, so trimmed and NativeAOT applications no longer need a custom converter. `[assembly: InquiryJsonContext(typeof(AppJsonContext))]` sets the context for the assembly, and `[InquiryJson(Context = typeof(...))]` overrides it for one property. Without either, `[InquiryJson]` keeps the reflection-based converter. `INQ108` reports a context type that is not a `JsonSerializerContext`. `INQ110` reports a property type that the context does not declare with `[JsonSerializable]`, or declares for serialization only. Inquiry never falls back to reflection. A new NativeAOT compatibility page in the documentation lists the supported combinations.
- `[InquiryWhere]` criteria can bind to method parameters by name. Set `Parameter = nameof(x)` on each criterion that takes a value, and `UpperParameter` for the upper bound of `Between` and `NotBetween`. Attribute order still sets the Boolean structure, and the generated SQL is the same as the positional form. Swapping two parameters of the same type no longer swaps the filters. A specification names its parameters as strings. On a set-based update, the update values can then appear in any position. Positional binding is unchanged and stays supported. `INQ109` is a new build error for an invalid named binding: mixed named and positional criteria, an unknown or unused parameter, a parameter bound twice, or a parameter on `IsNull` or `IsNotNull`.
- `[InquiryStoredProcedure]` methods can return `Task<IReadOnlyList<TEntity>>`. The call runs the procedure once and buffers every row of its result, like an ordinary select. An empty result returns an empty list. The shape works with the Oracle cursor wrapper and with SQL Server table-valued parameters. Before, it reported `INQ005`. Combining it with `OutputParameter`, `ReturnsValue` or an INOUT parameter reports `INQ051`, because rows and a read-back cannot share one method.

### Changed

- `INQ112` is a new warning for a method whose positional criteria bind two or more parameters of the same type, such as `string category, string name`. Builds that treat warnings as errors fail on these methods. Set `Parameter = nameof(...)` on each value criterion, which leaves the SQL unchanged, or suppress `INQ112`.

- **Breaking:** Results of handwritten SQL and stored procedures now map to properties by column name, not by SELECT-list position. Before, reordering two columns of the same type compiled and put each value in the wrong property. Names compare without regard to case, and extra columns are ignored. A missing column, or two columns that match one property, throws `InvalidOperationException` before the first row is returned. The message names the type, the property and the available columns. A database `NULL` in a non-nullable property, a column of an incompatible type, or an exception from a value converter, throws `InvalidOperationException` that names the property and the column, with the original exception as `InnerException`. Generated store queries keep their fixed column lists and are unchanged. To upgrade:
  - `[InquiryAdHoc]` DTOs: give every SELECT expression an alias that matches its property name, such as `SUM(Amount) AS TotalAmount`.
  - Entities read through `IInquiry.QueryAsync`, `QueryListAsync` and `QuerySingleOrDefaultAsync`: return each column under the entity's mapped name from `[InquiryColumn]` or `[InquiryKey]`. A column named after the property does not count when the mapped name differs. Select every mapped column, for example with `SELECT *` or the generated column list.
  - Stored procedures declared with `[InquiryStoredProcedure]`: make the procedure's result columns use the entity's mapped column names. Column order no longer matters.
  - `[InquiryProjection]` types read through handwritten SQL: return each column under the property's `[InquiryColumn]` name.
  - Code that catches `InvalidCastException`, `FormatException`, `OverflowException` or a converter's exception around these reads: catch `InvalidOperationException` and inspect `InnerException`.
- **Breaking:** `INQ106` is a new build error for two properties of an `[InquiryAdHoc]` DTO or an `[InquiryProjection]` whose column names are equal without regard to case, such as `Id` and `ID`, or two projection properties with the same `[InquiryColumn]` name. Both would claim one result column. Rename one property, or give it a distinct `[InquiryColumn]` name.

### Fixed

- PostgreSQL columns declared with `[InquiryColumn(SqlType = "jsonb")]` or `SqlType = "json"` now accept writes. Before, Inquiry sent the value as `text`, and PostgreSQL rejected inserts, updates, upserts and batch writes with "column is of type jsonb but expression is of type text". Bulk inserts failed with "unsupported jsonb version number". Inquiry now binds these columns as `NpgsqlDbType.Jsonb` or `NpgsqlDbType.Json`, for `[InquiryJson]` properties and for plain `string` properties. JSON-path predicate values, and parameters inside a longer `[InquirySet]` expression, still bind as text. `Compare.In` and `Compare.NotIn` on a whole `json` or `jsonb` column are not supported.

## [1.0.0-preview.12] - 2026-10-21

### Fixed

- Store methods that share a name now get generated SQL constants and per-method lookups keyed by their full signature. A key lookup overloaded with an unfiltered, distinct, locked, or filter-bypassing select previously ran that sibling's `SELECT`-all query and returned a row for a missing key.
- Native bulk insert disposes its dedicated connection when a telemetry listener throws after the connection opens. A failed open now records `connection.open_failed` with `error.type` instead of `connection.opened`, and keeps the open error.
- `RecordCommandText = false` now also redacts provider error messages from span status descriptions and `Error` logs, and drops `db.collection.name`, on command, grid, batch, bulk-insert, and transaction routes. Exception types stay recorded.
- `db.collection.name` reports the table for bracketed, double-quoted, backtick-quoted, escaped, and two- or three-part names. It handles newlines, tabs, and comments around keywords, uses the outer `SELECT`'s `FROM`, and recognizes `INSERT OR …`, `INSERT IGNORE`, `UPDATE OR …`, and `UPDATE TOP (n)`. Derived tables, table-valued functions, and unsupported shapes get no tag instead of a wrong one.
- When cancellation wraps a driver error, spans add `inquiry.error.cause.type` with the driver exception type. `error.type` stays `System.OperationCanceledException`.
- `QueryMultipleAsync` and generated eager loads now raise registered command interceptor callbacks, with or without an ambient transaction. `CommandExecutedAsync` runs when the grid reader is disposed; `CommandFailedAsync` runs once when execution or a read fails or is cancelled. Grids still record one `QUERY_MULTIPLE` telemetry span and metric.
- Eager loading matches `byte[]` relationship keys by value. Separately read rows with equal keys previously returned no related rows.
- Relationship and junction foreign keys resolve by exact C# property name in validation, SQL and parameter binding. A column name or another casing reports `INQ040` or `INQ088`, which now names the property to use, and no eager loader is generated for the relation even when the error is suppressed. A junction whose column names collide with other property names now joins the named properties.
- Relationships whose key columns store values differently report `INQ104` instead of compiling a join that matches no rows. This covers an enum stored as text against a numeric column and two different value converters. A converter on one side only, such as a typed ID, is not checked.
- Junction foreign keys whose `[InquiryForeignKey]` target contradicts their position report `INQ105`. Junction keys without that metadata keep positional pairing.

### Added

- `INQ103` warns when `JunctionTable`, `JunctionSchema`, `ParentColumn` or `ChildColumn` is set on an explicit-junction `[InquiryManyToMany]`, where it has no effect.

### Changed

- MySQL and MariaDB bulk inserts that complete with server warnings throw `InquiryBulkInsertWarningException`, still an `InvalidOperationException`. It reports the rows written, whether they are in the caller's Inquiry transaction, and the warnings. Telemetry records the written row count.
- Packages that use SQL Server or SQLite now depend on Microsoft.Data.SqlClient 7.0.3 or Microsoft.Data.Sqlite 10.0.12. The core package now depends on version 10.0.12 of the Microsoft.Extensions configuration, dependency injection and logging abstractions.
- The bulk insert guide describes per-provider transaction ownership, SQL Server per-batch commits, partial outcomes and safe retries. The testing guide no longer says that native bulk insert is always rejected in a sandbox.
- The batch operations guide explains that `MaxBatchSize` splits entity collections into commands but never limits input, and that SQL Server table-valued parameters are not chunked.
- The select declarations guide adds recipes for optional category filters and user-selected sorting. The stored procedure guide corrects its examples and limitations, and the runtime contract documents grid reader callbacks.

### Security

- The Aspire, Oracle, SQL Server and Testing packages now declare `System.Security.Cryptography.Pkcs` 10.0.13 on every target framework, which fixes GHSA-846f-f764-76mx and GHSA-2fmv-rv2c-59x7 in the version their ADO.NET drivers pull in. Consumers on .NET 8 or .NET 9 that pin an older 8.x or 9.x Pkcs will see a package-downgrade warning until they move up.

### Fixed

- Ordinary updates preserve soft-delete markers and affect only active rows. Archive and restore advance concurrency tokens; repeated transitions affect no rows. Archive-returning reports only affected rows on all six providers. Key-only restore remains an administrative operation without an expected-token check.
- Filter and audit scopes reject out-of-order disposal without losing the active scope. Repeated or copied disposal is harmless within each async flow.

- Transaction handles use their own execution pipeline. Command parameter collections are snapshotted consistently, and expanded collection parameters avoid name collisions.

- Managed concurrency rejects unsupported token shapes, including decimal, enum and DateTime, with `INQ101`; string/GUID stamps require explicit rotation.
- `[InquiryInsert]` and `[InquiryUpdate]` now infer batch operations from entity collection parameters. The separate `[InquiryInsertAll]` and `[InquiryUpdateAll]` attributes were removed.
- Insert, update, upsert, and key-delete methods now infer returning behavior from `Task<TEntity?>`; the `ReturnEntity` attribute property was removed. `[InquiryHardDelete]` and `[InquiryHardDeleteAll]` replace `HardDelete = true`.
- Generated batch and bulk-copy descriptors now expose one constructor per supported shape. Runtime-only generated-command and batch-command state is internal.
- `SqliteInquiryFixture` moved from `Ignyte.Inquiry.Testing` / `Inquiry.Testing` to the new `Ignyte.Inquiry.Sqlite.Testing` package and `Inquiry.Sqlite.Testing` namespace. Add the new package and update the fixture's using directive; keep `Ignyte.Inquiry.Testing` if you use its other helpers.

Use the corresponding `InquiryCommand` overload with `new InquiryCommand(sql, command => bindParameters(command, args))`; retain the materializer for typed queries and remove `TArgs` from the method's type arguments. Rebuild generated stores against the updated packages.

- Aspire's `AddInquiryMariaDb`, `AddInquiryMySql`, `AddInquiryOracle`, `AddInquiryPostgreSql`, `AddInquirySqlite`, and `AddInquirySqlServer` extensions now return `IHostApplicationBuilder` instead of `void`. Rebuild assemblies that call them; existing statement calls remain valid.
- `IInquiry.BulkInsertAsync` now has one overload with optional `InquiryBulkInsertOptions`. Change a third positional cancellation-token argument to `cancellationToken: token` (or pass `null` for options before the token), update custom implementations to the options signature, and rebuild callers.
- Runtime command execution, Oracle finalization and JSON array parameter formatting avoid unnecessary work.

## [1.0.0-preview.6] - 2026-08-03

First changelog-tracked preview. Earlier previews (`1.0.0-preview.3` through `.5`) predate this
changelog and the immutable-tag ruleset; their artifacts remain on nuget.org.

### Added

- Compile-time SQL source generator with six database providers (SQLite, SQL Server, PostgreSQL, MySQL, MariaDB, Oracle).
- Full CRUD operations: insert, select, update, delete, and upsert with parameterized queries.
- Transactions via `IInquiryTransaction` with `BeginTransactionAsync` and `ExecuteInTransactionAsync`.
- Eager loading for one-to-many, many-to-one, and many-to-many relations via grid reader.
- Many-to-many eager loading across all three junction shapes: an explicitly-mapped junction, a composite-key related entity, and an auto-managed junction whose table the generator synthesizes into the schema DDL. An auto-managed junction is read-only.
- Stored procedure support with OUTPUT, RETURN, INOUT parameters, multiple result sets, Oracle REF CURSOR, and SQL Server TVP parameters.
- Batch mutations with provider-selected transports (TVP, unnest, multi-row VALUES, individual commands).
- Bulk insert via provider-native copy APIs.
- A uniform cancellation contract across single commands and batch DML: when a cancel races provider completion, both a lying success and a native driver error normalize to `OperationCanceledException` carrying the caller's token, with the driver exception preserved as the inner exception. Work that genuinely completed before the token fired is never re-labelled cancelled, including a durably committed batch.
- Paged select with `InquiryPagedResult<T>` paired SELECT+COUNT return shape.
- WHERE predicates: comparison, IN-collection, LIKE, BETWEEN, IS NULL, full-text search, JSON containment.
- JSON-path querying: an `[InquiryWhere]` criterion with a `JsonPath` compares the dialect's JSON extraction of that path against the bound parameter instead of the whole column.
- ORDER BY with offset/keyset pagination.
- Projections, aggregations, DISTINCT queries, and column-list constants for raw SQL.
- Ad-hoc DTO materialization via `InquiryAdHocAttribute`.
- Database view support via `InquiryViewAttribute`.
- Computed columns via `InquiryComputedExpressionAttribute`.
- Generated store interfaces via `InquiryGenerateInterfaceAttribute`.
- Schema DDL generation and live schema fidelity testing.
- Optimistic concurrency via row-version columns.
- Pessimistic row-level locking with `InquiryLockMode` (update, share, skip-locked, no-wait).
- Soft delete with boolean-flag and timestamp indicators, global filter suppression.
- Named global filters via `[InquiryGlobalFilter(Name = "…")]` with a compile-time per-method bypass via `[InquiryIgnoreFilter("…")]`; an unknown, blank, or duplicated name is a build error (INQ091, INQ092) rather than a silently widened query.
- Runtime-parameterized global filters via `[InquiryGlobalFilter(ContextKey = "…")]`, bound from an ambient `InquiryFilterContext.BeginScope(…)` instead of a constant column. Reads without an ambient scope throw `InquiryFilterValueMissingException`; misconfiguration is a build error (INQ093). Key-based writes do not compose the filter by default; set-based predicate writes do.
- PostgreSQL row-level-security session helpers: `SetLocalAsync` on `IInquiryTransaction` sets a transaction-scoped custom GUC (via parameterized `set_config(…, true)`) that an RLS policy reads with `current_setting`. Transaction-only by design — applied outside a transaction the setting simply does not survive to the next statement (`SET LOCAL` warns and no-ops; `set_config(…, true)` expires with the implicit statement transaction), so policies read an unset parameter and queries silently return zero rows. The setting is discarded at commit or rollback, so no `RESET`/`DISCARD` is needed.
- Opt-in write-side enforcement via `[InquiryGlobalFilter(EnforceOnWrites = true)]`: the filter's predicate is AND-composed onto key-based update, delete, hard delete, restore, batch delete, and hard predicate delete, so a write aimed at a row the filter hides affects zero rows. Inserts stay unfiltered and the column is never auto-stamped; upsert on such an entity is a build error (INQ095) because its insert branch cannot be filtered. Rows-affected 0 now conflates not-found, stale concurrency token, and filtered-out. Stores that do not opt in generate byte-identical SQL.
- Audit columns (`InquiryCreatedAt`, `InquiryCreatedBy`, `InquiryModifiedAt`, `InquiryModifiedBy`) with `InquiryAuditContext`.
- JSON and array column mapping with provider-native types.
- Value converters for custom CLR-to-database type mappings.
- Sequential GUID generation (COMB) with correct sort order per provider.
- Parameterized `FormattableString` SQL execution via `InquirySql.Sql()`.
- Prepared statement mode control via `PreparedStatementMode`.
- NativeAOT compatibility across all providers.
- Provider compatibility modes: `AzureSql`, `CockroachDb`, `AuroraPostgreSql`, and cloud-hosted modes for MySQL, MariaDB, and Oracle.
- OpenTelemetry tracing, metrics, and ILogger structured logging via `AddInquiryTelemetry()`.
- Transient-fault retry and per-provider backup-server failover.
- Health checks for all providers.
- Data seeding via `IInquiryDataSeeder` with `AddInquirySeeder<T>()` and `SeedInquiryAsync()`.
- Dependency injection with `AddInquiry()` service collection extensions and provider-specific `AddInquirySqlServer()` / `AddInquiryPostgreSql()` / etc. registration.
- ASP.NET Core audit-context middleware via `UseInquiryAuditContext()` for stamping `CreatedBy`/`ModifiedBy` from the current user identity.
- Interceptors package with slow-query logging, sqlcommenter trace-context tagging, and N+1 query detection.
- Testing package with SQLite fixture, recording interceptor, entity factory, transaction sandbox, and Respawn reset.
- Roslyn analyzer diagnostics (INQ001–INQ095) for compile-time validation.
- [Column encryption](docs/site/articles/features/column-encryption.md) — application-side encryption as a value converter (encrypt in `ToProvider`, decrypt in `FromProvider`), with a worked `AesGcm` example, the loss of filtering and indexing on the ciphertext, and the SQL Server Always Encrypted / PostgreSQL pgcrypto alternatives. No new API; the existing converter seam carries it.
- [GraphQL DataLoader recipe](docs/site/articles/features/graphql-dataloader.md) — batching Hot Chocolate resolver fan-out onto a single `Compare.In` predicate method.
- [Migrations recipe](docs/site/articles/features/migrations.md) — using `InquiryGeneratedSchema.Ddl` as the baseline script for DbUp or FluentMigrator, plus `ProviderArtifactsDdl` and `ProviderArtifactsValidationSql` for deploying and checking the SQL Server TVP types.
