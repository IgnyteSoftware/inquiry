# Generator benchmark comparisons

Research for #396, collected 2026-09-09. These are recommendations for measurement and release review, not accepted 1.0 limits or evidence that Inquiry has passed them.

## Recommendation

Use 25, 100, and 500 entities **per consumer project**. Treat 100 as the proposed primary acceptance workload, 25 as the small-project check, and 500 as the large-project stress check. This is a proposed product scope, not a claim about the distribution of .NET applications. Keep all three in the evidence report. If 500 fails, record the result and obtain an explicit supported-scale decision before signoff.

Use Dapper AOT as the closest external comparison for generating database command and row-reading code. Use Mapperly to check source-generator measurement methods. Use EF Core for model complexity and consumer-build context, but do not borrow its application-startup numbers as generator latency limits.

The sources reviewed do not establish a portable millisecond budget for a 25-, 100-, or 500-entity generator. Collect matched measurements before proposing numeric limits. #396 must remain open until the supported workload and candidate acceptance limits are approved and verified.

## What the comparisons actually measure

| Comparison | Useful evidence | Limit on the comparison |
| --- | --- | --- |
| Dapper AOT | Generates interceptors, row factories, and command factories. Compare the same result shapes, parameter shapes, and query call sites. | It consumes SQL and Dapper calls. Inquiry also derives SQL and tracks entity relationships. Entity count alone does not equalize the work. |
| Mapperly | Its source-generator benchmark loads real projects before measurement, then measures generation with allocation reporting. | Object mapping is not an ORM workload. Its benchmark does not measure a clean MSBuild invocation or an edited, primed driver. |
| EF Core compiled models | Provides a concrete large relational model and a consumer workflow that produces C# code. | Model optimization and application startup are different phases. Neither is an incremental Roslyn edit benchmark. |
| Inquiry with captured generated source | Builds the same compiler input with the generator omitted and its previously generated files supplied. | Isolates generation overhead, not the cost of compiling generated code. Use the corresponding generated snapshot after each semantic edit. |

Dapper documents the three generated components and their roles in reading results and binding parameters. That makes it a useful overlap comparison, not a feature-equivalent replacement. The captured-source comparison is a proposed local control. [Dapper AOT generated code](https://aot.dapperlib.dev/generatedcode.html)

Mapperly's benchmark uses `MSBuildWorkspace` in setup and calls `RunGeneratorsAndUpdateCompilation` on a stored driver during measurement. It does not save the returned driver or apply edits. Its `Compile` and `LargeCompile` names therefore describe fresh generation on prepared compilations in a running process, not full consumer builds. [Mapperly benchmark source](https://github.com/riok/mapperly/blob/f87d48b12a6010a224ca26ad112fb48c07cd6d5d/benchmarks/Riok.Mapperly.Benchmarks/SourceGeneratorBenchmarks.cs)

Mapperly also compares benchmark results with a saved baseline in CI. The inspected workflow uses a `300%` alert setting. This demonstrates a regression-checking mechanism, not a suitable Inquiry release allowance or an industry latency standard. [Mapperly benchmark workflow](https://github.com/riok/mapperly/blob/f87d48b12a6010a224ca26ad112fb48c07cd6d5d/.github/workflows/benchmark.yml)

## Why 500 entities is a useful stress point

EF Core documentation describes large models as hundreds to thousands of entity types and relationships. Microsoft's compiled-model example has 449 entity types, 6,390 properties, and 720 relationships. A 500-entity test is consequently a credible large-model probe, but a sparse fixture is not equivalent to that example. [EF Core compiled models](https://learn.microsoft.com/en-us/ef/core/performance/advanced-performance-topics#compiled-models), [Microsoft's 449-entity example](https://devblogs.microsoft.com/dotnet/announcing-entity-framework-core-6-0-preview-5-compiled-models/)

The example's roughly 2-second initial result and 257-millisecond compiled-model result measure application startup work. They do not measure code generation, clean build, or editor feedback. Do not turn those numbers into #396 thresholds. [Measurement description](https://devblogs.microsoft.com/dotnet/announcing-entity-framework-core-6-0-preview-5-compiled-models/)

Report properties, relationships, store methods, projections, DTOs, source-tree count, and generated bytes alongside entity count. Start with the repeatable sparse fixture, then add a representative relationship-rich consumer before claiming the large-model case is covered.

EF query precompilation is an optional secondary comparison. Its documentation describes a publish-time workflow, warns that the feature is experimental, and says interceptor generation is not intended for the editing loop. It cannot establish an editor responsiveness budget for Inquiry. [EF Core precompiled queries](https://learn.microsoft.com/en-us/ef/core/performance/nativeaot-and-precompiled-queries)

## Keep the measurement boundaries separate

1. Measure fresh driver generation on a prepared compilation with latency, allocations, and output counts. Call this warm-process fresh generation. Creating a new driver does not reset JIT or process state.
2. Measure unrelated, one-model, and related-model/filter edits from the same primed driver. Each invocation must start from that baseline, not from the result of the previous identical edit. Verify generated source and compilation outside timing.
3. Measure clean and post-edit consumer builds as separate compiler-process operations. Restore dependencies outside the measured build and report that choice. Record compiler-server reuse, SDK, runtime, CPU, memory, configuration, analyzer versions, and generated source size.
4. Measure actual editor feedback separately if making an IDE claim. Record editor version and generator execution mode. A driver benchmark omits editor scheduling, cancellation, diagnostics presentation, and other extensions.

Roslyn's documented pipeline caches intermediate values between runs. Its cookbook stresses value equality so unchanged information can stop downstream work. This supports checking bounded output invalidation after edits; it supplies no universal elapsed-time limit. [Incremental generator design](https://github.com/dotnet/roslyn/blob/221af6c9126020b1412ac0f34596391cf57ff335/docs/features/incremental-generators.md), [Roslyn cookbook](https://github.com/dotnet/roslyn/blob/221af6c9126020b1412ac0f34596391cf57ff335/docs/features/incremental-generators.cookbook.md)

A Roslyn maintainer explicitly distinguishes persisted IDE generator state from command-line builds, which run generation from scratch when compilation occurs. An up-to-date build that skips compilation is not evidence of a fast generator edit cycle. [Roslyn discussion #71441](https://github.com/dotnet/roslyn/discussions/71441)

BenchmarkDotNet's default throughput strategy measures steady-state operations after pilot and warmup work. `ColdStart` omits those stages, but multiple iterations can still mix first and later calls. For a process-cold claim, use one measured generation per fresh process and state whether process launch is included. [BenchmarkDotNet run strategies](https://benchmarkdotnet.org/articles/guides/choosing-run-strategy.html)

## How to choose release limits

Run Inquiry, the captured-source control, and a pinned Dapper AOT version on the same quiet reference host. Keep result shapes and query call-site counts equal in their shared subset. Report Inquiry-only relationship and filter work separately. Use Mapperly's actual sample and integration project only as a methodology check, not a normalized entity-count result.

Capture raw samples and repeated process launches. Compare medians and spread before selecting a regression tolerance. Report tail latency only with enough independent observations to support the stated percentile. Retain allocations and generated bytes as independent signals, since latency alone can conceal unnecessary work.

Propose two kinds of limits after this baseline exists:

- An absolute user-facing build and edit budget for the approved 100-entity consumer on the named reference machine.
- A candidate-versus-approved-baseline regression allowance, with an absolute noise floor, applied to each measured operation and supported size. Choose the allowance from observed repeatability and acceptable cost, not Mapperly's CI alert setting.

Also report the 25-to-100 and 100-to-500 growth ratios. Investigate growth beyond the increase in fixture work before signing off scalability. An unrelated edit should not re-emit unrelated output, even if its elapsed time happens to fall below a budget.

For build attribution, enable `ReportAnalyzer` and detailed MSBuild logging alongside wall-clock samples. The compiler documents this option for analyzer execution-time information. Keep its reported timings separate from total build elapsed time. [C# compiler reporting options](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/compiler-options/errors-warnings#reportanalyzer)

The release decision should name the workload, host, versions, statistic, absolute limit, regression allowance, and evidence artifact. Record unsupported or failing sizes explicitly. Research and diagnostic results do not close the acceptance gate.
